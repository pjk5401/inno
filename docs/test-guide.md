# 교수님 시연 및 현장 검증

## 바로 시작

1. VM 메뉴 13번으로 테스트 환경 실행.
2. `/test/staff/login/`에서 초기 관리자 로그인.
3. 테스트 제어 → 기본 테스트 준비.
4. 테스트 QR 화면을 랩탑에 표시. 교수님마다 가상 학번/이름 배정.
5. 교수님은 휴대폰 기본 카메라로 QR 스캔. 첫 가상수업 선택 → 배정 정보 → 서명 → 제출.
6. 진행자가 테스트 출석 현황과 Excel 두 버전을 확인.

초기 가상수업은 모두 10:00–11:00이며 시계는 10:00부터 정상 흐른다. 기본 위치 모드는 ‘모의: 구역 안’. 실제 위치 권한 테스트를 원하면 인정 구역 설정 후 ‘실제 위치’로 전환하고 새 QR로 접속한다.

## 브라우저 학번 제한 확인

### 같은 휴대폰에서 다른 학번이 출석된 경우

원인 확인 전에 테스트를 초기화하지 않는다. 담당자의 ‘테스트 제어 → 브라우저 출석 진단’ 또는 출석 상세의 ‘브라우저 출석 진단’에서 두 기록의 브라우저 번호와 회차를 비교한다. 번호는 서버가 발급한 등록 코드이며 휴대폰 고유번호가 아니다. 다른 번호만으로 사용자가 다른 브라우저를 썼다고 단정하지 않는다.

진단 추가 전 기록도 기존 Attempt 연결이 남아 있으면 번호와 회차를 표시하지만 과거 쿠키 상태는 복원할 수 없다. 진단 버전 `2026-10-23-1` 배포 이후에는 최신 QR로 접속 → Safari 닫기 → 다시 최신 QR로 접속한 뒤 ‘최근 QR 접속 20건’의 두 행을 비교한다. 출석 제출·초기화 없이 확인할 수 있다.

- 쿠키 미수신: 서버에 브라우저 쿠키가 도착하지 않음. 브라우저 저장 상태·접속 호스트/경로·프록시 등을 구분하여 조사한다.
- 쿠키 서명 불일치/만료/형식 오류: 쿠키는 도착했으나 검증에 실패함. 서명 키 변경, 쿠키 변형, 유효기간 등을 조사한다.
- 쿠키 검증 성공 + 재사용: 기존 브라우저 등록이 유지됨.
- 쿠키 검증 성공 + 새 등록: 해당 등록이 DB에 없음. 테스트 초기화 등과 대조한다.

쿠키 원문·QR 토큰·IP·사용자 에이전트는 진단 기록에 저장하지 않는다. 진단 페이지는 관리자와 조교에게만 제공한다. 이 진단 기능은 쿠키가 없어도 동일 기기를 찾아내는 기능이 아니다.

### 정상 흐름

1. 테스트 전체 초기화 후 ‘정상 출석’, ‘모의: 구역 안’을 선택한다.
2. 휴대폰에서 최신 QR → 첫 가상수업 → `20260001 / 가상학생01` → 서명·제출한다.
3. 같은 브라우저로 QR을 다시 촬영한다. 학번이 `20260001`로 고정되고 입력을 수정할 수 없어야 한다.
4. 두 번째 가상수업에 제출한다. 같은 학생의 수업별 출석 두 건이 저장되어야 한다.
5. 학생 입력·완료 화면에 ‘학번 변경’이 없는지 확인한다.
6. 조교가 ‘수업·명단’ → 해당 수업 → 가상학생02 이름을 선택한다. 현장 확인을 가정해 ‘수동 처리·정정’에서 출석·인정 시각·사유를 저장한다.
7. 가상학생02의 기록이 수동 처리로 표시되고 새로운 서명이 생성되지 않았는지 확인한다. 기존 가상학생01의 출석과 브라우저 학번은 유지되어야 한다.
8. 시각 시나리오를 바꿔도 학번이 유지되는지, 전체 테스트 초기화 후에는 새 QR에서 다시 학번을 입력할 수 있는지 확인한다.

QR을 다시 찍을 때 동일한 브라우저를 사용한다. 카메라가 여는 브라우저와 별도의 인앱 브라우저는 쿠키가 공유되지 않을 수 있다. 다른 학번 요청을 서버에서 차단하는 검사는 자동 테스트에 포함된다.

## 수업 삭제 확인

1. 테스트 환경에서 가상수업 하나에 출석·서명 기록을 만든다.
2. 수업 목록의 ‘삭제’ 또는 수업 상세의 ‘수업 삭제’를 선택한다. 명단·출석·서명 수가 맞는지 확인한다.
3. ‘취소’를 선택하면 자료가 유지되어야 한다.
4. 다시 삭제 화면을 열고 수업명·사유를 입력해 삭제한다. 해당 수업은 목록과 학생 선택 화면에서 사라지고 다른 수업의 자료는 유지되어야 한다.
5. ‘변경 이력’에서 처리자·삭제 수업·대상 수·사유를 확인한다. 삭제했던 학생의 기존 완료 화면도 더 이상 기록을 보여주지 않아야 한다.
6. 삭제 확인 화면을 연 뒤 다른 휴대폰으로 출석을 추가해본다. 기존 확인 화면에서 삭제하면 변경 안내가 표시되고 즉시 삭제되지 않아야 한다.

운영에서도 같은 삭제 기능을 제공한다. 삭제된 자료는 웹에서 되돌릴 수 없으므로 실습에는 테스트 환경을 사용한다. 전체 테스트 초기화로 기본 가상수업을 다시 만들 수 있다.

## 실제 위치 확인 절차

아이폰 Safari, 안드로이드 Chrome에서 각각 시험한다. 실제 권한 허용/거부, 실내·입구·인정 구역 경계, 와이파이/모바일 데이터를 점검한다. 위치 정확도 허용값은 기본 150m이며 구역 반경과 별도로 조정한다. 구역을 과하게 넓혀 해결하지 말고 실제 결과를 보고 결정한다. 인앱 브라우저 문제 시 기본 브라우저로 연다.

## 데이터·권한 확인

- 운영 DB에 수업 한 개를 만들고 테스트 초기화 후 운영 기록이 유지되는지 확인.
- 학생이 담당자 URL에 접근하면 로그인 화면으로 이동하는지.
- 조교 계정으로 시스템/계정 페이지 접근 시 403인지.
- 간단 Excel에 서명이 없고 서명 Excel에 실제 제출한 이미지가 들어가는지.
- 학번 `001234`가 엑셀/화면/재등록에서 유지되는지.
- 수동 정정 사유와 처리자가 남고 두 담당자의 동시 수정이 충돌 안내되는지.
- 같은 세션의 통신 재시도는 최초 기록을 반환하고 중복 생성하지 않는지.

## VM 동시 접속·복구 확인

실제 운영 전 테스트 환경을 초기화한 뒤 VM 메뉴 16번으로 기본 가상학생 200명의 HTTP 제출을 점검할 수 있다. TEST 확인과 테스트 운영 계정 로그인이 필요하며 데이터를 자동 삭제하지 않는다. 기본 24개 동시 작업으로 3수업에 분산 제출하고 성공/실패/평균/p95 시간을 출력한다. 동일 데이터를 재사용하면 중복 제출 오류가 나므로 반복 전에는 테스트를 초기화한다. 더 강한 동시성 시험은 `scripts/load_test.py --workers 32` 등으로 조정한다. 실제 위치 권한 대기·사용자 입력 시간은 이 도구가 재현하지 않는다. 요청 실패·중복·기록 누락은 현황/엑셀에서도 확인한다. 로컬 SQLite 자동 테스트를 PostgreSQL 동시성 검증으로 간주하지 않는다.

백업/복구는 운영 데이터가 없는 초기 VM에서 먼저 시험한다. 테스트 출석 → 백업 → 데이터 변경 → 해당 백업 복구 → DB와 서명 일치 및 계정 로그인 확인. 80포트 충돌, 재부팅 후 재시작, 디스크 부족 동작도 확인한다.
